# SOL AI 架构说明与隔离边界

日期：2026-09-09

分支：`codex/sol-ai-trading-system`

状态：**隔离阻断修复后，现已获准完成公共行情驱动的 PAPER 闭环，进展见 [PAPER 验收](PAPER_ACCEPTANCE.md)。下面的隔离规则与第 9 节验收边界继续有效；生产实盘仍硬关闭，真实服务器未部署。此前只离线验收的记录保留在 [历史隔离验收报告](ISOLATION_ACCEPTANCE.md)。**

## 1. 核心决策

`sol-ai-trading-system` 是独立交易系统，不是原跟单后端中的一个运行插件。

**只复用代码能力，不复用线上数据、配置、连接、实例或运营状态。** 即使原模块导出的函数看起来只负责下单，只要其传递依赖会加载旧数据库、账户配置或交易服务，就不得直接导入。

- 原跟单服务、数据库、账户日志、定时任务和运行参数保持不动。
- 新系统部署到另一台服务器，拥有自己的进程、依赖、配置、密钥、数据库、日志和运维生命周期。
- 不连接原数据库，包括只读连接、备库、数据库代理、共享缓存、数据卷和数据库导出备份。
- 不通过原跟单后台 API 间接读取账户配置或执行下单；原系统不是新系统的执行网关。
- 默认仅 `dry_run: true` 模拟交易。填入 API Key、启动服务、打开网页、环境变量或数据库旧值均不能开启实盘。
- 本轮仅允许隔离修复、离线/mock 测试和受控本机验收，不继续策略功能开发、不部署、不创建验证订单。

## 2. 部署与调用关系

```text
                    统一管理网页 / HTTPS 入口
                    ├─ 原路径 ───────► 服务器 A：原跟单后端
                    │                         └─ 原数据库 / 配置 / 日志 / 状态
                    │
                    └─ /sol-ai/ ────► 服务器 B：SOL AI FastAPI
                                              ├─ 公共行情订阅
                                              ├─ 指标 → 策略 → 独立风控
                                              ├─ 默认：PaperBroker
                                              ├─ 手动实盘：本机专用执行桥
                                              │             └─ Binance 专用交易账户
                                              └─ 独立数据库 / 日志 / 报告 / 状态

      服务器 B  ──禁止访问──► 服务器 A 的数据库、状态目录、执行接口
```

代码复用发生在研发构建阶段：审查纯源码 → 固定版本快照 → 纳入新模块 → 独立构建。
新服务器运行时不需要原仓库 `server/`，不加载原服务，不扫描原配置，不执行原数据库迁移。

## 3. 复用点与禁止复用项

| 能力 | 允许复用的部分 | 必须隔离或重新实例化的部分 |
| --- | --- | --- |
| Binance 请求 | 签名、请求编码、错误解析、原 ID 查询的协议代码 | API Key、HTTP 客户端、时钟校准、配额计数均属于新进程 |
| 下单与撤单 | 参数构造、数量精度、价格精度、订单/止损接口调用代码 | 新订单 ID、新提交记录、新订单状态机；不委托旧执行服务 |
| 风控 | 无数据库依赖的风险金额、止损距离、精度等计算函数 | 新权益、日亏损、次数、连续亏损、持仓、熔断和审批记录 |
| 日志 | 格式化、结构化字段、脱敏函数 | 新 logger 实例、新文件/轮转配置、新日志索引；不读取旧日志 |
| 对账 | 查询/解析和幂等处理的代码模式 | 只恢复新系统自己产生的原订单 ID、提交日志和成交记录 |
| 前端 | 展示组件、样式、导航能力 | 数据请求指向各自后端，令牌和操作权限分离 |

明确禁止复用：旧数据库连接池、ORM 实例、Repository、账户配置加载器、全局服务容器、持仓归属表、冻结风险基线、订单 outbox、实盘执行状态、监控任务、锁、缓存、Telegram 队列、运行开关和旧会话。

“不复用状态”并不禁止请求工具在**新进程**中维护自己的限流或时钟缓存；禁止的是共享、恢复或导入旧进程的状态。复用函数应显式接收依赖，不隐式读取宿主环境。

## 4. 源码复用边界

当前采用 `bridge/vendor/` 固定源码快照加显式隔离补丁，不整体导入原 `BinanceAdapter`。源、输出、补丁哈希均记录，正常构建不需要原仓库。

当前原适配器存在以下传递依赖：

```text
server/exchange/binance-adapter.ts
  → server/exchange/guarded-order.ts
    → server/risk-gate.ts
      → server/db.ts
```

即使只需要其中的签名或下单方法，也不能通过这个模块入口导入。

现有快照来源包括原适配器中摘取的请求/精度声明，以及 `safe-request`、`symbol-loss-policy`、`full-margin-stop`、`logger`、`credential-redaction` 的源码；其中 `full-margin-stop` 快照目前未进入执行桥 bundle。

后续强制规则：

1. 来源、摘取声明、源文件及输出 SHA-256 进入 manifest。哈希证明来源一致，不代表安全审查通过。
2. 刷新快照必须显式执行并审查差异；正常构建只核验已固定快照，不自动拉取旧代码。
3. 生产包不得包含旧数据库模块、旧入口、旧 `.env`、生产数据或指向原目录的符号链接。
4. 同时检查 Python 导入、Node 传递依赖、动态加载和最终构建输入；不能只依赖几个禁止关键词。
5. 在原仓库、原数据库和原服务均不可访问的环境中完成独立导入与模拟运行验收。

## 5. 配置、数据和运营状态隔离

以下为隔离布局；仅在对应模式获准运行时创建状态，默认不创建 live 状态：

```text
/opt/sol-ai-trading-system/
  config.yaml                  # 仅新系统行为配置
  .env                         # 仅新系统专用密钥，0600
  trades/
    paper/ledger.sqlite3       # 模拟余额、订单、持仓、风控状态
    live/ledger.sqlite3        # 新系统实盘状态，独立于 paper
    live/bridge-submissions.jsonl
  logs/paper/                  # 独立模拟日志
  logs/live/                   # 独立实盘日志
  reports/                     # 只由新系统账本生成
```

- 不使用仓库根 `.env`，不向上查找，不从父进程环境回退获取交易密钥，不接受 `${...}` 引用宿主密钥。
- 行为参数只取新配置；日志级别、限流参数也不得隐式继承旧服务环境。
- 数据目录应做规范化路径、符号链接和所有者检查，必须落在新实例允许目录中；禁止外部数据库 URL、共享卷和旧目录。
- 数据库创建/迁移只能发生在路径和实例身份检查通过后。模拟/实盘模式冲突必须在任何写入前拒绝。
- 实例标识、配置版本、策略状态、暂停/熔断、交易日统计、幂等键和恢复游标全部独立持久化。
- 只迁移新模块自己的 schema；升级和回滚不能执行旧仓库的部署脚本或迁移脚本。
- 日志、交易文件、数据库、备份和真实 `.env` 不进入 Git；只有源码、配置模板和审计文档可交付。

## 6. 默认模拟与手动实盘边界

默认配置必须保持：

```yaml
dry_run: true
live:
  enabled: false
  confirmation: ''
  dedicated_account_confirmed: false
```

模拟模式的行情可以来自 Binance 公共接口；成交、止损、止盈、余额和盈亏均在新模拟账本中计算。模拟进程不得创建实盘客户端或调用任何账户私有接口，默认部署也不启动执行桥。不要求配置 Binance Key。

未来实盘开启必须由操作人手动修改**新模块自己的** `config.yaml`，同时满足 `dry_run: false`、`live.enabled: true`、明确确认文本和专用账户确认；凭据仍只在新 `.env` 中。网页不提供绕过这些条件的实盘开关。

所有真实下单必须经过新策略风控和提交前二次审批。执行桥在实际写请求前重新核验配置，缺项、格式错误或未开启即拒绝。测试全部使用模拟传输，不发送验证订单。

这些开关不是恢复旧实盘状态的入口。新系统只对自己的订单、持仓与保护单负责；遇到非本系统订单或仓位应停止新开仓并告警，不自动接管、平仓或删除。

**账户隔离同样必要：**同一个交易所账户的两个 API Key 仍共享余额和持仓。仅换服务器、数据库、API Key 或订单前缀不能隔离交易资产。未来实盘应使用与旧跟单账户分离的专用账户/子账户，并核验账户身份；人工勾选确认不能替代身份核验。此核验不需要连接旧数据库。

## 7. 基础设施与管理网页

- 新服务器使用独立 `sol-ai` 用户、虚拟环境、Node 依赖、服务名、端口和备份；没有原服务器数据库凭据或共享磁盘。
- 通过网络策略明确阻断访问旧数据库、缓存及执行服务；仅允许所需公共行情、未来获准的交易接口、可选 Telegram 和管理连接。
- 本机执行桥仅监听 loopback，不暴露给浏览器或统一管理网关。管理 API 保留独立认证。
- 网页合并只代表入口/展示合并：浏览器或网关分别请求两个后端；不能让新后端读取旧 DB，也不能把旧下单 API 当作复用模块。
- 第一阶段使用独立管理凭据，不依赖旧登录数据库。以后如需统一登录，必须另行设计仅传身份、不传交易密钥的授权边界。
- 任何新模块部署、停止、升级、回滚均只操作新服务器；旧服务不参与、不重启。

## 9. 恢复开发后的隔离验收清单

1. 将新模块单独复制到无原源码、无旧服务、无旧数据库网络权限的环境，完成安装、导入和模拟启动。
2. 依赖检查拒绝旧 `db`、ORM、服务入口、全局配置及任何通向旧目录的传递/动态依赖。
3. 使用假凭据哨兵测试：宿主环境、父目录 `.env`、`${...}`、符号链接、外部路径均不能成为配置/密钥/数据来源；不使用真实生产凭据测试。
4. 默认模式即使存在新 API Key，也只有公共行情流量；没有账户读取、下单、撤单、杠杆设置或保护单写入。
5. paper/live 使用不同账本与日志，模式不符在任何文件/schema 写入前拒绝，重启只恢复当前新实例状态。
6. 实盘门禁在模拟传输测试中覆盖缺项、错误类型、环境变量覆盖、请求中途关闭与配置损坏，均不能绕过。
7. 使用合成订单证明未知结果只查询本系统原 ID，不导入旧历史、不接管非本系统仓位；止损失败路径单独验收。
8. 新服务器网络/文件权限拒绝旧系统访问；新服务退出、升级、回滚不会影响旧服务。
9. 统一网页两个入口各自认证和路由，SOL AI 后端不存在调用旧执行接口或旧数据库的代码。
10. 全部通过后才能申请新的模拟部署验收；实盘仍需操作人另外手动开启，不由测试自动开启。

本轮仅对上述隔离清单进行修复和验收，不据此恢复策略功能开发。第 8 项真实新服务器验证以及实盘身份/生命周期验收尚需独立完成。
